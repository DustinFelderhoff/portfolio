Enterprise AI Invoice Parser

AI Zero-to-One Failure Story
One of the first enterprise ChatGPT deployments. Built trust from zero, watched it break, then rebuilt it with the team that had to use it.
The Call

I pushed a bleeding-edge LLM tool live before building trust with the ops team. I traded user confidence for speed. Shipping a working tool doesn't matter if the people using it don't trust the output.

Challenge

In 2022, our audit operation sent PDF invoices to India to be typed into Excel by hand. Error-prone. Auditors spent 30 hours a week reconciling data-entry mistakes. Customer feedback loop was measured in days. ChatGPT had just launched, unproven in enterprise, especially on structured financial data. No playbook existed.

Process

Built a ChatGPT-based parser that understood expected value ranges for each invoice field and extracted them into audit-ready data. Designed a prompt/skill system so the model could flag anomalies when a number fell outside its expected range. One of the earliest enterprise LLM deployments, and I had to make it up as I went.

Then I shipped it without training the India ops team on the exception workflow. The model would occasionally hallucinate a line item amount or swap vendor names on low-resolution scans. Not often, but the team didn't know which outputs were reliable and which weren't. Within two weeks they were flagging every edge case manually. No trust in the AI output. The system was technically correct but operationally broken.

Hard Lesson. The Fix

Building the right tool isn't enough. The people using it have to trust it. I pulled the automation back and ran three hands-on training sessions with the India team over Zoom. We redesigned the exception workflow together: a confidence-score threshold on every extraction so low-confidence results queued for human review instead of auto-accepting. The ops team defined the threshold. They also chose which fields were "must match exactly" versus "best effort." Second launch stuck because they owned the guardrails. Trust took longer to build than the software.

Lesson Learned

Leading the tip of AI means being wrong first. No one had done this before. The skepticism was warranted. What made it work wasn't the technology. It was iterating on the human workflow around it until trust caught up with capability.

Autonomous Sub-Agent Orchestration System

Agentic AI System Design
Four agent personas, strict handoff contracts, and a routing system that enforces boundaries.
The Call

I restricted the four agent personas to strict toolset whitelists instead of letting them do whatever they wanted. It traded raw flexibility for predictable safety. I didn't let the parent trust the child's work and forced independent verification on every side effect.

Challenge

Agent systems that let sub-agents do everything eventually break in unpredictable ways. A researcher with filesystem access overwrites config files. An implementer with web search goes down rabbit holes. What I needed: a routing system where agents have strict boundaries, handoff contracts are enforced, and the parent verifies every artifact the child claims to have produced.

Process

Designed four specialized sub-agent personas: researcher, implementer, architect, operator, each with its own toolset whitelist, max iterations, blocked actions, and trigger keywords. Built a routing decision tree that determines whether to handle a task natively, delegate to a single specialist, or orchestrate a mixed workflow. Every delegation boundary follows a handoff contract: the parent sends a self-contained goal + context + toolset, the child returns summary + errors + artifacts + verification, and the parent independently verifies every side effect.

Lesson Learned

Never trust a sub-agent's self-report on side-effectful operations. The handoff contract says "the parent verifies." When a child claims it wrote a file or ran a command, the parent reads the file back or stats it. This caught multiple instances where a child "succeeded" but the artifact was empty or misnamed. Verification isn't optional. It's the architecture.

Lesson Learned

Tool boundaries are the architecture. The most important design decision wasn't what each agent could do. It was what each agent couldn't do. Blocking the wrong tools prevents entire failure classes. A researcher with filesystem access will eventually overwrite something. An implementer with web search will go down rabbit holes. The boundaries define the system.

Story Sundays

Agentic AI Shipping
A full-stack storytelling platform for my son and his grandparents. Privacy-first, AI-powered, built from scratch.
The Call

I chose to build a custom full-stack platform from scratch instead of relying on social media. Total data privacy for my family was non-negotiable. I also took a hard line on quality by enforcing a multi-layer testing pipeline after we realized a green mocked test suite still let real bugs slip into production.

Challenge

My son was born. Grandparents in Texas and Florida had no way to share stories and videos that felt personal, safe, and permanent. Social media meant data leakage, algorithm feeds, and zero ownership. What I needed most: a private space where AI could drive family storytelling without leaking anything outside the family circle.

Process

Built a full-stack platform from scratch. React 19 frontend, Cloudflare Workers API layer, Supabase Postgres with row-level security, R2 for media storage. The architecture uses a gated TDD pipeline (unit, hooks, integration, e2e:prod) with circuit breakers: if the same error repeats twice, the system stops, researches root cause, and escalates. Three test layers catch what mocks miss. AI transcribes and organizes memories but never exposes them outside the family's contacts window.

Lesson Learned

A green test suite isn't proof a bug is fixed. We shipped bugs that slipped past a fully green mocked test suite. 6 entries in the bug ledger prove it. That's why the project now enforces multi-layer testing with hard gates. A test that passes against mocks but fails in production is worse than no test at all: it gives false confidence.

Lesson Learned

Circuit breakers, not caffeinated retries. When a step fails: root cause first, research the exact error with real version numbers, evaluate each candidate for credibility and blast radius, then apply. Never retry the same error twice without research. This killed the thrash loop problem: the wasted "try X, fail, try Y, fail, try Z" pattern that costs hours.

System Architecture Optimization & Context Lifecycle

Agentic AI Infrastructure
Tool schema refactoring, context compression, guardrails, and orchestration. A system-level audit.
The Call

The hard call wasn't just buying more compute to fix the memory caps. We forced the system to auto-compress its own context at an 85% threshold using four strict retention classes. We risked dropping useful old data, but we had to stop the agent from drifting into loops.

Challenge

A production agent system with 65 tools across 26 toolsets. Context was ballooning, memory was hitting caps, and the system had no automated way to decide what to keep, what to learn, and what to throw away. Without a protocol, every session started fresh, repeating the same mistakes.

Process

Ran a full architecture audit across four pillars: (1) tool schema refactoring that trimmed verbose descriptions to save token budget, proposed 4 new tool types; (2) context compression and memory decay, building a retention-class system (CRITICAL, DURABLE, SESSION, EPHEMERAL) that auto-decides what to keep and compress at 85% capacity; (3) pre-execution guardrails: 4 silent checks run before every tool call (shell safety, file safety, delegation integrity, sequence integrity); (4) sub-agent orchestration, which is the routing system described above.

Lesson Learned

Context management is the unsexy bottleneck of every agentic system. The difference between a tool that works reliably and one that drifts into loops is how well it manages its own context. The retention-class system taught me that most "memory" problems are classification problems. If you know what to keep, what to learn as a skill, and what to throw away, context collapse becomes rare instead of inevitable.

Autonomous Job Application Pipeline

Agentic AI Automation
Discovery through voice-gated generation. Per-company research, zero AI tells.
The Call

The hardest call was slowing down the pipeline to prioritize a voice gate over raw volume. I risked speed to guarantee every application actually sounded human and bypassed AI detectors. Sending out thousands of generic resumes that just get auto-rejected is a waste of time.

Challenge

Job hunting is a data problem: hundreds of roles, scattered sources, variable quality, and every application needs to sound like a human. Generic applications don't work. What I built: a system that discovers roles, evaluates fit, researches each company's actual pain points, and generates materials that sound like one specific person.

Process

Built a multi-stage pipeline: Tavily AI Search + SearXNG for discovery, a custom scoring engine with time-decay and location penalties, research sub-agents that investigate each company's competitive gaps, and a voice-of-me gate (canonical transcript to anti-ai-detection scan) that ensures every output sounds human. Single SQLite jobs.db as source of truth. Research workers discover what the company is behind on, not just JD keywords.

Lesson Learned

Voice is the hardest thing to automate, and it's the most important thing to get right. The pipeline can generate a technically perfect letter that still reads like AI. The voice-of-me skill (built from a canonical transcript of how I actually talk) plus anti-ai-detection (catches structural tells like space-dash-space, balanced paragraphs) turned out to be the most valuable components, not the scoring engine. Every piece of copy must pass both gates, in order, or it doesn't ship.

Lesson Learned

A pipeline with no feedback loop is a liability. The location penalty was supposed to downrank non-Remote jobs outside Denver. But if the scraper didn't extract the real location from the JD, the penalty didn't fire. Now every research worker verifies location as a hard gate before scoring. One layer of validation is never enough.

Next Best Prompt Engine

AI Product Dev Algorithm Design
Designed and iterated a recommendation algorithm for a family story-sharing app — from basic MVP through industry research to a hybrid A+B architecture, all documented with cited sources and interactive HTML stakeholder presentations.
Problem

A daily prompt system was using a basic "exclude seen + balance categories" algorithm. Users reported prompts felt repetitive and didn't account for real life events — birthdays, new family members, milestones. Different generations also seemed to prefer different recommendation styles.

Process

Researched recommendation systems from Netflix (multi-layer personalization), Duolingo (Thompson Sampling bandits + spaced repetition), Anki/SuperMemo (SM-2/FSRS algorithms), and competitors like StoryWorth and Remento. Built three algorithm candidates with different tradeoffs. Presented findings in an interactive HTML format for stakeholder review.

Outcome

User rejected "pick one" and proposed a hybrid approach. Final architecture: Life Event Override Layer (birthdays, anniversaries, re-engagement) → Dual-Track A/B (EOSRS vs Thompson Sampling, compared weekly) → MVP fallback. Zero ongoing LLM cost. User feedback: "This is a Great BRD to showcase the Product Development decision."

Product Principles

The patterns that hold up across every project. These started as engineering lessons and turned into PM strategy.

1. Trust matters more than the tech stack.

Invoice Parser · Story Sundays · Job Pipeline

The Invoice Parser was technically sound the day it shipped. It didn't stick until the ops team trusted it. Story Sundays enforces a gated pipeline because a green test suite gave false confidence. In every project, the hardest problem was the same: how do I build something people actually trust, not something that technically works? The answer is always iteration, training, and transparency, never just better code.

2. What you exclude defines what you ship.

Sub-Agent Orchestration · Context Management

The most impactful product decision in the orchestration system wasn't what each agent could do. It was what each agent couldn't do. A researcher with filesystem access will eventually overwrite something. The same rule applies to product scope: the retention-class system works because it explicitly defines what not to keep. Saying no to features, access, and scope creep isn't constraint. It's architecture.

3. Velocity requires guardrails.

Story Sundays · System Architecture

The thrash loop (try X, fail, try Y, fail, try Z) is the most expensive pattern in any build, not just code. Story Sundays enforces a "same-error-twice" rule: if the problem repeats, stop and research the root cause before trying another guess. This turned hours of wasted cycling into targeted fixes. The principle: speed without a stopping condition isn't velocity. It's chaos with a budget.

4. AI adoption is really a change management problem.

Invoice Parser · Charter (KIRO)

When I brought ChatGPT into an enterprise audit workflow in 2022, the technology was the easy part. The hard part was getting the team to trust the output, building workflows around exceptions, and training people who had been doing it one way for years. Every AI project since has confirmed this: the value of an AI system is multiplied by how well the humans around it can use it, not by how clever the model is.

5. Ship fast enough to learn, gate hard enough to protect.

Invoice Parser · Story Sundays · System Architecture

The Invoice Parser shipped early and broke. Story Sundays ships through a gated pipeline with circuit breakers. The architecture optimization shipped as incremental skills and cron jobs. The pattern: ship fast enough to learn, but gate hard enough to protect the user. The gating mechanisms get more sophisticated with each project, but the first-mover advantage of being early with AI has been consistently valuable.

6. Never trust a handoff without verification.

Sub-Agent Orchestration · Job Pipeline

When a sub-agent says "I wrote the file," the parent reads it back. When a research worker says "I found the data," the pipeline checks the output. This sounds obvious but it's the most commonly skipped step, because trust is faster, because it usually works. Until it doesn't. In product work this is the same as: when engineering says "it's done," you test it yourself. Verification at every handoff boundary is the only reliable way to ship.
