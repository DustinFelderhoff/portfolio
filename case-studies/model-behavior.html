Where this started

The moment that changed how I build came from a bug that should never have shipped. A few weeks into running a multi-agent build pipeline, code kept reaching my family's app that passed every test and still misbehaved in production. The pipeline was green. The app was wrong.

It took me a while to see why. The agent that wrote the code was also the agent that wrote the tests, and both were judged by whether the tests passed. That's not verification. That's a model grading its own homework. The code was correct by construction, because the test was written to match whatever the code did.

The fix wasn't a better prompt. It was a change to how the system behaves. Separate who builds from who verifies. Give each role a fresh context so no one can talk themselves into an answer. Lock a failing test before any code is written, and certify only when the real system, not a mock, produces the change.

That reframe is the discipline this page is about. The Browser Company calls it Model Behavior. It's the work I've been doing every week on my own product for months, and it's the work I'd bring to Dia.

How an AI agent should behave toward people

Story Sundays is a private family storytelling platform I built for my son and his grandparents. Its whole reason to exist is how it treats people: their voices, their memories, their privacy. That shapes every behavior decision I make. I want my son to hear his grandmother's voice when he's older, the way she told a story, not just the words on a screen. Nothing in that product can leak outside the family, or the product betrays its purpose.

The AI Family Assistant is where agent behavior becomes user-visible. It runs on a Cloudflare Worker with a React panel and routes through OpenRouter. It's contextually aware of family members and their stories, so it can ask a meaningful follow-up instead of a generic one. Deciding how that assistant should talk, what it may access, and when it should stay quiet is a behavior problem, not a prompt problem.

The same care shows in the build system that makes the product. When a model is trusted to produce irreplaceable family recordings, the rules around who can change what, and who verifies it, are the product's real safety surface.

Model choice is a behavior decision

The Browser Company picks a model or a harness the way a PM picks a feature, because it changes what the user experiences. I reached the same conclusion by watching mine fail.

The expensive version. I ran an 8-agent Claude Code setup built around a CrewAI pattern, mixing Claude Code with DeepSeek Pro and MiMo. It was powerful and pricey. By early July 2026 I canceled the Claude Code subscription on cost and kept the pieces that earned their keep.

The lean version. From then through late July I paired GLM-5.2 for reasoning with DeepSeek Flash for fast, deterministic work. That pairing carried the build through the next stretch of releases.

The split that stuck. Since late July I've run a 5-role cycler: DeepSeek Pro handles architecture, planning, and complex reasoning, and DeepSeek Flash handles the deterministic jobs like verification, linting, and docs. This looks like a cost call, but it's really behavioral.

A cheap fast model is great at checking whether something is true. It's bad at deciding what is worth building. A strong reasoning model is the reverse. Let the cheap model do the deciding and it cuts corners. Let the big model do the checking and it's slow and still grades its own work. Splitting the roles stopped the self-grading failure and killed the thrash loop.

Role separation is enforced structurally, not by hope. Each role hands off in a fresh context. A Test-Author Protocol locks a failing test before any code is written. A deterministic verifier diffs the result against that locked state. No model gets to claim success on its own say-so.

Evals are how I steer quality

I don't treat tests as a checkbox. I treat them as evals that steer the product, and I place each one where it can actually observe the behavior it's guarding. The stack has four layers:

Unit

Fast checks on single functions and pure logic. Good for catching local mistakes early.

Hook-integration

Runs against a real Postgres instance, not a mock, so data behavior is tested where it lives.

Integration

Validates Row Level Security and multi-tenant isolation, the privacy boundary of the whole app.

E2E

Playwright drives the real UI on desktop and mobile, exercising the product the way a person would.

The doctrine is blunt: a green test suite isn't proof a bug is fixed. I only certify at the layer that can observe the behavior in question, and I forbid mocking the seam under test. If a test passes against mocks but fails in production, it's worse than no test at all, because it sells false confidence.

That philosophy is backed by about 1900 lines of edge-case documentation, where every invariant is tied to a test at the layer that can see it. When an ambiguous rule could go either way, the doc says which way and why, so the next model and the next human don't have to guess.

I ship changes to real users every week

This isn't a demo. In 13 weeks the product moved through 165 versioned releases, which works out to more than twelve a week. Each one goes through a gated pipeline with circuit breakers. If the same error repeats twice, the system stops, researches the root cause, and escalates instead of blindly retrying. Core invariants have seen zero regressions through all of it.

  • 600+ passing tests across the four layers
  • 165 versioned releases in 13 weeks, roughly 12+ per week
  • 20+ database migrations with full RLS coverage, no data leaks
  • 8 major feature areas shipped to active alpha users

The tools I live inside, and why

A Model Behavior person should be able to talk about their own stack the way they talk about the product. Here's mine, honestly.

I build inside Hermes, an agent platform, and opencode for task routing, where I direct model traffic by job. I've routed work through models like deepseek-v4-flash and muse-spark-1.3. I use GLM-5.2 for creative and analytical generation where its reasoning depth beats a faster model. I run a humanizer gate on everything I publish, because catching AI tells in your own output is how you learn to spot them in a product's output too.

The through-line is the same as in the product: pick the cheapest model that can do the job reliably, and spend the expensive reasoning where judgment matters. Then prove it worked rather than assuming it did.

A failure that made the product better

I've already owned the self-grading failure. There's a second one worth registering. Earlier, at a previous job, I pushed an AI audit tool to production before training the operations team on how to handle exceptions. Within two weeks they were flagging everything, because they didn't trust the output. The system was technically correct and operationally broken. I pulled it back, ran hands-on training, and rebuilt the exception workflow with their input. The second launch stuck.

Lesson: the behavior of an AI system includes how the people around it learn to trust it. Ship the model and the onboarding together, or the model fails on human terms no matter how accurate it happens to be.

What I'd bring to Model Behavior

I'd bring a working answer to the questions the team already wrestles with. A browser agent that reads your tabs, drafts your replies, and runs your morning brief is a system that has to decide what to trust, what to surface, and when to stay out of the way. That's the same judgment I exercise on the AI Family Assistant and in my build pipeline, where a wrong call can damage a real family's memory or leak their data.

I'm a product person who works inside the prompts, the harnesses, and the evals every week, and who ships changes that reach users continuously. Give me an ambiguous behavior problem and I'll break it into something measurable, build the eval that steers it, and tell you when a one-line prompt change is enough versus when the system itself needs to change.

And I care about how software treats people, because the browser is the doorway to the rest of their life. That's why the family product I built is private by design. I'd bring the same care to deciding how an agent treats a user's attention and their data.
