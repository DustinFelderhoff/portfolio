### Phase 6: LinkedIn Content Strategy (~30 min)

**Step 6.1** — Draft 8 LinkedIn posts (2/week × 4 weeks) in `linkedin-content-plan.md`.

Voice: Direct, first-person, no buzzwords. Each post ties a specific product/building lesson from Story Sundays / Hermes Agent to a PM hiring signal. Topics:

| Week | Title | Angle |
|------|-------|-------|
| 1.1 | Trust > Tech Stack | Story Sundays users trusted an AI with private family stories. Building trust wasn't about the model — it was about knowing what the AI *couldn't* do. Hiring signal: PMs who prioritize user trust over shiny tech. |
| 1.2 | Exclusion as Architecture | The most important decision in Hermes Agent wasn't what tools it got — it was what it *couldn't* touch. Defining boundaries > defining capabilities. Hiring signal: PMs who design constraints, not features. |
| 2.1 | Velocity Needs Guardrails | Shipping fast without gates creates chaos. Circuit breakers, same-error-twice rules, verification-as-a-service. Speed without safety isn't velocity. Hiring signal: PMs who build systems that let teams move fast without breaking things. |
| 2.2 | AI Adoption = Change Management | The invoice parser failed not because the tech was wrong, but because the nurses using it didn't trust it. AI adoption is a change management problem dressed up as a technical one. |
| 3.1 | Ship Fast + Gate Hard | The invoice parser shipped early and broke. Story Sundays ships through a gated pipeline. The pattern: ship fast enough to learn, but gate hard enough to protect the user. First-mover advantage with AI is real, but only if you survive the first mover's mistakes. |
| 3.2 | Verify Every Handoff | An agent that reports success and an agent that actually succeeded are two different things. Every handoff needs a verifier that doesn't trust the other agent's report. Lessons from building multi-agent orchestration. |
| 4.1 | The Feedback Loop Blind Spot | Location penalty didn't fire because the data wasn't there. One layer of validation is never enough. The lesson applies to any AI product: build feedback loops into every step, or you're flying blind. |
| 4.2 | Building for the Person Using It | Started in manufacturing, building production lines where operators could produce great output without fighting the system. That same instinct drives every product: the person using it should feel more capable when they're done. |

**Step 6.2** — Save to `linkedin-content-plan.md` in `/c/Users/dusti/portfolio_repo/.hermes/plans/` alongside the main plan.

## Risks

| Risk | Likelihood | Mitigation |
|------|-----------|------------|
| Shared CSS breaks on first load (FOUC) | Medium | Inline a tiny critical CSS snippet in `<head>` above the stylesheet link (just `:root` variables + `body` background). This is already how the site works — no FOUC risk since CSS is the first thing loaded. |
| deploy_ai_news.py nav template breaks | Low | The script generates ai-news pages from Python string templates. Only the nav template needs the Apply link removed. CSS template stays untouched — ai-news pages are standalone. |
| AI news bottom-nav doesn't have Principles/Lessons | Low (pre-existing) | The deploy script's bottom-nav template (lines 260-266) already omits Lessons/Principles and Apply. This is fine — it was tailored for ai-news subdirectory navigation. Don't "fix" it. |
| Sub-page bottom-nav differs from index.html bottom-nav | Low (pre-existing) | Sub-pages use file links (`about.html`, `projects.html`) while index.html uses anchor links (`#about`, `#projects`). This is by design for sub-page navigation. Don't normalize them. |
| case-studies/next-best-prompt-engine.html breaks | Low | Only 173 lines with its own minimal inline CSS. Not changing its CSS — risk is zero. |
| Relative path mismatch on styles.css for subdirectories | Low | All 6 manual pages being changed are in the repo root. case-studies/ page is not being modified. ai-news pages are generated by deploy script and keep inline CSS. No relative path issues. |
| Git state/CI conflict | Low | No CI/CD exists (GH Pages pushes directly). Test locally before `git add` and `git push`. |

## Implementation Script

For efficiency, the implementer should use `patch` (find-and-replace) or `sed` for the nav removals (identical pattern across 6 files) rather than editing each file manually in an editor. The CSS extraction can be done by copying the inline `<style>` content from index.html to styles.css, then running the removal + link-insertion across all pages as batch operations.
